Call for call

The portal makes the same calls we do

Worth being precise about why: isV2() is a per-request flag on the same controllers, and an action name resolves to a method on that same class. The portal and this server run identical handlers. Neither interface has a composite endpoint the other lacks, so the API calls needed to finish a job are the same number on both sides. What differs is who has to remember the sequence.

Remove a user
2+1+ncalls
  1. GET /domains/{domain}/phonenumbersfind DIDs routed at this user
  2. GET /domains/{domain}/agentsfind their queue memberships
  3. DELETE /domains/{domain}/users/{user}cascades to 10 object types
  4. DELETE /domains/{domain}/phonenumbers/{phonenumber}per orphaned DID
  5. DELETE /domains/{domain}/callqueues/{callqueue}/agents/{agent-id}per orphaned membership

The delete alone leaves calls 4 and 5 undone, and nothing in the response tells you they exist.

What changed

Seven ways the surface used to dead-end

Each of these was a tool the model could pick and never complete, or worse, one that reported success while doing nothing. Left is what happened before; right is what happens now.

What
Was
Now
Forwarding calls
Sent rule-action and forward-destination, which appear nowhere in the spec or the source. NetSapiens ignored them and answered success.
Sends forward-always, the field the controller actually reads. A conformance test fails the build if a composite invents a field name again.
Every write
Returned 202 with an empty body before replicating, so create-then-read raced and the model reported failures that never happened.
synchronous=yes on all 32 operations that accept it, so a write is readable when it returns.
Adding a user
Wrote the user record only. No device to register a phone, no number to reach them on.
provision_user runs user, device, DID in order and names what is still unconfigured.
Staffing a queue
Wrote the queue and hunt group. No agents, so nothing answered. Missing the description the controller requires, so it 400'd.
provision_call_queue adds each agent and the DID, and always sends a description.
Removing a user or queue
Cascaded generously, but never to DIDs routed at the target or its queue agent rows. A deleted user left numbers routing at nothing.
Both deprovision_* tools inventory the leftovers first, then release them. dry_run shows the plan.
Media uploads
12 tools sent JSON to endpoints that parse a raw upload. Guaranteed failure, with nothing suggesting another route.
Hidden from search and rejected with the working alternative named: text-to-speech or base64 for greetings, music, images.
Hold messages
The one family with no upload-free variant. Reading and deleting worked; creating one was impossible from here.
set_hold_message sends a real multipart upload from base64 audio, for a domain or a single user.
Still true of the platform

The cords the API leaves plugged in

Two of the delete cascades stop short, and they stop short in the portal too. Delete a user and their devices, contacts, addresses, timeframes, voicemail and MFA all go. The DID routed at them does not, and neither does their row in a call queue. Delete a queue and its agent memberships survive it.

A DID that resolves to a deleted destination
is worse than one that resolves nowhere,
because the dial plan keeps answering.

We cannot fix that in the platform, so the composites clean up after it, and do the cleanup even when the delete itself failed. A half-deleted user with live DIDs is the worst of the available states.

Next

The one gap left is efficiency, not reach

01
Enrich the spec at generation time

The controllers honor fields, limit, start and sort far more widely than the vendored spec declares, and carry 1,743 parameter descriptions plus 269 per-endpoint permission annotations the spec does not. One generator change improves every tool at once.

02
Thread field selection into the composites

find_user pulls a thousand full records to match on five fields. deprovision_user lists every number in the domain to find one. Both get cheap the moment sparse fieldsets are available.

03
Expose the call center statistics tree

Three routes exist in the router and in none of the spec, with 44 metric definitions behind them: handle time, speed of answer, service level, after-call work, agent time in state. The model still cannot see any of it.
