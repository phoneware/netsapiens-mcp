These endpoints perform every write themselves. Wrapping them in a client-side composite would add failure modes and buy nothing, so we deliberately ship no composite for any of them. The generated tool is the whole operation.

Chain run by the client

The portal walks you through it. The API does not.

Here the endpoint writes one piece and stops. In the portal these are a wizard or a screen with several panels; through a bare API they are separate calls in a specific order, with a half-built object waiting if you stop partway. Each one is a composite in our catalog.

Platform behavior, not ours

The cords that stay plugged in

Two of those deletes leak the same way, and they leak in the portal too. The record is gone; the route to it is not. A DID that still resolves to a deleted destination is worse than a DID that resolves nowhere, because the dial plan keeps answering.

Delete a user

Devices Released
Contacts, addresses, timeframes Released
Voicemail, MFA, CDR schedules Released
DIDs routed to the user Still live
Call queue agent rows Still live

deprovision_user reads both before deleting, then releases them, and does the cleanup even if the delete itself failed. A half-deleted user with live DIDs is the worst of the available states.

Delete a call queue

Call queue row Released
Hunt group row Released
Every agent membership Still live
DIDs routed to the queue Still live

deprovision_call_queue removes the agents first. Once the queue row is gone, the membership endpoint has no queue to address and those rows are unreachable through the API at all.

Write semantics

Every write used to race the replica

NetSapiens writes take a synchronous flag that defaults to no. With no the API answers 202 with an empty body before the write has replicated far enough to be read back. Any flow shaped create it, then read it back raced that: the model wrote, re-read, found nothing, and reported a failure that never happened.

32 operations declare the flag.
26 of them mark it required.
0 of our calls used to send it.

The tell was in the platform's own code: NetSapiens sets synchronous=yes on the subscriber create inside the auto attendant chain, precisely because the six steps after it read that subscriber back. We now default it on every tool whose schema accepts it, and an explicit value always wins.

Next

What the source says to do next

01
Enrich the spec at generation time

The controllers honor fields, limit, start, and sort far more widely than the vendored spec declares, and carry 1,743 parameter descriptions plus 269 per-endpoint permission annotations the spec does not. One generator change improves every tool at once.

02
Thread field selection into the composites

find_user pulls a thousand full records to match on five fields. deprovision_user lists every number in the domain to find one. Both become cheap the moment sparse fieldsets are available.

03
Expose the call center statistics tree

Three routes exist in the router and in none of the spec, with 44 metric definitions behind them: handle time, speed of answer, service level, after-call work, agent time in state. The model cannot currently see any of it.
